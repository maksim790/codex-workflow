# Prepare Task

Create a reviewable Markdown task ticket in the target Git repository's existing project vault. For a large request, create a main ticket and linked, verifiable child tickets when their boundaries are settled. The user later passes a ticket's title, filename, or Tasks-relative path to `$start-task`. A ticket records the requested outcome and evidence-backed acceptance contract; it is not an implementation plan, ADR, architecture page, or proof that checks ran.

## Locate and inspect

1. Use the active Git repository unless the user names another target. Inspect `git status --short` and preserve existing staged, unstaged, and untracked work. Read applicable `AGENTS.md`, its documentation navigation, and the existing vault `Home.md`. Confirm the vault path from project evidence. If the vault is absent or ambiguous, ask for the path or suggest `$setup-project init`; do not create a parallel `docs/` tree.
2. Read only task-relevant vault pages, ADRs, source, tests, interface schemas, and command definitions. Treat code as evidence of current behavior, not proof of desired product rules. Distinguish explicit user requirements, verified repository facts with source links, inferences, and unresolved choices. Do not run unknown scripts, install dependencies, expose secrets, or alter application code.
3. Select an existing project Tasks directory if one is established; otherwise use `<vault>/12-Development/Tasks`. Put a standalone ticket at `<Tasks>/<descriptive-slug>.md`; use the grouped layout below for a new large task. Each path must resolve inside the intended vault and repository, including through symlinks or junctions. Use portable, distinct names. Do not create an index or empty taxonomy pages solely for tickets. Check every planned destination before writing; if a ticket or group path exists and the user has not requested its update, stop and ask whether to continue it or use a new name. Do not overwrite it, silently create a duplicate, or move existing flat tickets into groups without a separate request.

## Write the ticket

Use ordinary relative Markdown links so the ticket works in Obsidian, GitHub, and other Markdown readers. Include these essentials:

- **Title, creation time, and status:** Record `Created: YYYY-MM-DDTHH:MM:SSZ` using the current UTC time when first writing the ticket, and preserve that value on later updates. New tickets use status `draft`, `needs-decision`, or `ready`; `done` is set by `$start-task` only after verified completion. `ready` means the requirements and design decisions needed to start this ticket are resolved, required design and implementation-plan approvals are recorded, and the final scope review below is complete. It does not mean code or checks have been completed.
- **Goal:** the observable outcome and stated reason. Do not invent business intent.
- **Request and evidence:** summarize explicit user requirements and link to relevant code, tests, contracts, vault pages, and project instructions. Label inferences; report code/documentation conflicts rather than resolving them by guesswork.
- **Scope and constraints:** what is included, important exclusions, compatibility boundaries, and user restrictions. Omit exclusions that add no clarity.
- **Acceptance criteria:** numbered, observable outcomes and meaningful error or boundary cases. Do not encode an unapproved product choice as a criterion, even provisionally.
- **Architecture and contracts:** only task-relevant current boundaries and likely impact. Link to durable documentation instead of copying it; mark proposed changes and decisions as proposed.
- **Design and plan handoff:** when design or implementation-plan approval is required, link the approved artifact, identify the version or scope the user reviewed, and record the user's approval and which tickets it covers. A child may inherit approval from its main ticket only within that scope. Keep proposed artifacts and delegated technical choices distinct from user approval. Do not create an empty design or plan document for a task that needs neither.
- **Verification plan:** applicable approved project DoD gates and task-specific checks with actual command/source evidence where known. Label all as planned, unavailable, or unknown; never imply they passed.
- **Open questions and decisions:** record material unresolved choices with consequences and user decisions when supplied. Omit this section when none remain.

Keep the ticket concise for local tasks; add detail for consequential changes. Omit empty optional sections and invented placeholders. Resolve product behavior, contracts, and substantial architecture during preparation. Research first, make a concrete recommendation, and ask only for decisions the agent cannot responsibly make. Combine closely related blocking choices in one concise request when that reduces back-and-forth; do not serially ask about routine reversible technical choices. Record answers and their scope in the ticket. A material unanswered question or required but unapproved design makes the affected ticket `needs-decision`; a proposed design is not approval. You may write a useful draft while awaiting an answer, but do not mark it `ready` or invent the answer. When creative design needs Superpowers `brainstorming`, complete its design approval during preparation. When `writing-plans` applies, write its separate implementation plan during preparation and submit it for approval in the final review below; a saved plan alone is not approval. Do not code, run implementation checks, or choose the final Fast/Full mode here; `$start-task` does that against current evidence.

## Final scope review

After the material decisions and any required implementation plan are prepared, show the user **3–5 short bullets (fewer for a small task)** headed “Что будет сделано” before the final `ready` handoff. Describe the observable result and major deliverables or boundaries, not file edits or implementation steps. For a group, summarize the overall outcome and important child outcomes within the same five-bullet limit. Link the full plan when one is required and ask for one review of the scope and that plan; the short list does not substitute for making the plan available. If an invoked planning skill requires a choice of execution approach, capture that choice here separately from plan approval; never infer permission to delegate. Keep a new or explicitly re-prepared ticket `draft` while this review is pending; do not call silence approval. If the user changes the scope or plan, update the affected criteria, design, plan, and child tickets, resolve any newly opened decision, and repeat the review only for material changes. After the user accepts, record the approval, covered scope, and reviewed plan reference or revision in the ticket, then mark the affected tickets `ready` if their other gates also pass. This review does not replace a required design approval or authorize implementation or publication.

## Large requests

Keep one ticket when the request has one independently verifiable outcome. When it spans several substantial deliverables or boundaries, such as a new service plus contracts, data ownership, consumer integration, and deployment, prepare a main coordination ticket and smaller child tickets. Split by verifiable outcome and dependency, not by source file, technical layer, or a fixed number of tickets.

For a **new** large task, create `<Tasks>/<task-slug>/00-main.md`. Put children in the same folder as `01-<slug>.md`, `02-<slug>.md`, and so on. The two-digit prefix records the initial suggested order; the ordered list in `00-main.md` shows the current order. Explicit dependencies, not filename numbers, determine what can start. Do not rename existing files merely because the order changes; update the main list and links instead. Keep established flat tickets where they are unless the user separately requests a migration.

1. Identify the main ticket as coordination work. Put the overall goal, shared constraints, architecture decisions, approved design and plan references when applicable, integration acceptance criteria, and proposed sequence in it. If an unresolved product or architecture decision determines child boundaries, write **only** this main ticket as `needs-decision`. Label the breakdown as proposed, ask for the blocking decision, and do not create children that assume its answer.
2. Once the relevant boundaries are supported by repository evidence and explicit user decisions, create numbered child tickets for the agreed deliverables. Each child states its own outcome, scope, observable criteria, meaningful failure cases, verification plan, and dependencies. Link to the main ticket for shared decisions and approved design or plan instead of copying them; identify any child-specific approval still open. Link each child from the main ticket and check both directions. A child with its own unresolved question, design gate, or required plan approval stays `needs-decision`. Do not invent a dependency merely from numbering.
3. Order children by dependency and identify the first one to start. The main ticket coordinates the overall result and final integration; it is not an implementation task. Recommend `$start-task <task-folder>` to start the first open child without a separate selection. If that child has a blocking question or unmet dependency, `$start-task` pauses its implementation. If the user later asks to continue a `needs-decision` main ticket, reread it and current evidence before proposing focused updates and creating children. Preserve agreed requirements; obtain approval before changing them.

Writing a **new** ticket is authorized by the user's invocation of this skill. For a requested update to an existing ticket, inspect its content and Git state, propose the focused changes, and obtain approval before altering agreed requirements or decisions. Preserve unrelated human notes and existing ADRs.

## Handoff

Read every written ticket back, check relative links and Git diff, and report paths, statuses, evidence used, approved design and its scope when applicable, unresolved questions, and unverified assumptions. For a decomposed request, report the dependency order and the first child. Identify the exact task-group or standalone ticket path in the handoff so a bare `$start-task` in this same conversation can select it; also show `$start-task <task-folder>` or `$start-task <filename-or-Tasks-relative-path>` for use in a later chat. Do not claim code was implemented, tests passed, or the tickets were approved merely because files exist. Do not commit, push, create a PR, merge, or deploy without authorization for that action.
