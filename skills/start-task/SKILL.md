# Start Task

Coordinate a development task in the active Git repository. Use installed Superpowers skills for their own procedures; do not replace or summarize them as a new workflow. Use `$setup-project` separately for repository onboarding, documentation refresh, or a read-only architecture audit.

## Bare invocation: choose a ticket

When the user sends only `$start-task` with no task description or ticket reference, **immediately show the five most recently created open task entries** in the active repository's existing project vault. An entry is a standalone ticket or a grouped task's `00-main.md`, not every child in a group. This is a read-only selection step, not task execution; do not ask for a task description before listing, choose a ticket on the user's behalf, or start implementation.

1. Find the intended vault from applicable `AGENTS.md` and its `Home.md`. Use an established task directory if documented or evident; otherwise look in `<vault>/12-Development/Tasks`. Do not create a vault or task directory. Read ticket Markdown in that directory, not unrelated vault notes. Treat a subdirectory with `00-main.md` as one grouped entry; keep legacy flat tickets as standalone entries. Exclude `done` entries from this default open list, while allowing explicit lookup of them.
2. Rank entries by their ticket's `Created: YYYY-MM-DDTHH:MM:SSZ` UTC timestamp, newest first. For older tickets without a valid creation timestamp, use file modification time as an **approximate** fallback and mark that date as approximate. Break equal timestamps by repository-relative path so the list is stable. Do not infer creation order from ticket title, filename number, or status.
3. Display up to five numbered entries with title, status, creation date, a brief goal, and repository-relative path. For a group, show child progress from actual child statuses and its current ordered list; do not substitute filename order for explicit dependencies. Show fewer when fewer exist. If the vault or task directory is missing, ambiguous, empty, or has no open entries, say so and point to `$prepare-task` or request the vault path as appropriate; do not invent tickets.
4. Wait for the user's number or ticket reference. Resolve a reference as described in **Ticket handoff**. On selection, open that file and follow the normal task workflow, checking current evidence. If files changed since the list, recheck the selected ticket. Listing alone does not authorize task writes; selection authorizes normal local task work subject to its gates, but not publication.

## Start with evidence

1. Identify the target repository and task. Inspect `git status --short`, applicable `AGENTS.md`, relevant docs, source, tests, CI, and defined project commands. Preserve existing staged and unstaged work. Do not run unknown project scripts merely to discover their behavior. If the user supplied or selected a ticket reference, follow **Ticket handoff** below before recording the task contract.
2. Record a task contract: requested outcome, affected area, user constraints, observable acceptance criteria, unresolved assumptions, mode, and the evidence for that mode. Derive simple criteria from a direct request and code; for a ticket, reuse its recorded decisions and criteria without reopening them. Ask for a decision before dependent work only when business behavior, a breaking contract, or substantial architecture remains materially ambiguous after checking the ticket and current evidence. Obtain a decision before destructive data operations or production actions unless the user has already authorized that exact action.
3. If project `AGENTS.md` or an approved project DoD is absent, use verified repository evidence for this task and report `project DoD: unspecified`. Suggest `$setup-project` separately when useful; do not create project docs as a side effect.

## Ticket handoff

Treat an argument that looks like a ticket title, short name, filename, or path as a **ticket reference**. A clearly phrased request to perform new work remains a direct task request. If the intent is unclear, try ticket lookup first; do not silently treat an unmatched reference as a new implementation request.

Resolve a ticket reference before choosing a mode or implementing:

1. Find the intended vault and established Tasks directory as in **Bare invocation**. An existing explicit absolute or repository-relative ticket path takes precedence. Otherwise resolve a path such as `notifications-service/01-event-contract.md` relative to the Tasks directory; allow the `.md` suffix to be omitted. A reference matching a group directory opens its `00-main.md` for routing, not implementation. For a simple name or title, search Markdown tickets recursively under Tasks for an exact filename, filename stem, or first-level Markdown heading, ignoring case and differences between spaces and hyphens. Do not use substring or fuzzy matches to select a ticket.
2. Canonicalize the candidate path, including symlinks or junctions, and confirm that the existing Markdown file is inside the target Git repository, its intended vault, and the Tasks directory. Reject traversal and escaped links. If multiple tickets match, show their repository-relative paths and wait for the user's choice; never choose by recency. If none match, say `ticket not found`, show a few nearby names or paths as suggestions, and wait for a reference or an explicit direct task request. Do not create a ticket or start implementation from the unmatched text.
3. Open the resolved file before choosing a mode or implementing. Use its goal, constraints, and acceptance criteria as the proposed task contract, subject to the user's latest instructions and a focused freshness check of applicable `AGENTS.md`, linked decisions/design, and relevant source and tests. Read the approved design or parent decision record once when it covers this ticket. Preserve its stated evidence and decisions; `ready` alone is not proof of approval, but a recorded user decision or approved design covering this scope is. Do not repeat broad requirements discovery or ask the user to approve that same decision again while its assumptions still hold.

If a group directory, a grouped `00-main.md` path, or a listed group is selected, read the main ticket and child statuses/dependencies. `00-main.md` is coordination only: never implement it as a task, even on an explicit whole-parent request. If the main ticket is already `done`, treat the group as read-only unless the user asks to reopen or change it. If it has no agreed child tickets yet, report its preparation or decision gate and stop; an empty child list is not completed work. Otherwise choose the first child in the main ticket's current ordered list whose status is not `done`, then start that child immediately without asking which child to choose. One invocation starts one child; after completion, report the next and let a later group invocation continue. Do not skip an earlier open child because it is `draft`, `needs-decision`, or blocked: apply that child's normal decision/dependency gate and pause dependent implementation. If the main ticket lacks a reliable order or its first open child has an unmet dependency, report the inconsistency and stop instead of guessing a different child. A directly named child also cannot bypass unmet dependencies.

When all agreed children are `done`, a group or `00-main.md` invocation performs **verification only** of the overall integration criteria and applicable DoD. Close the main ticket if those checks pass. If verification reveals missing implementation, leave the main open and propose a focused child task or correction; do not implement missing work under `00-main.md`. An explicitly selected `done` ticket is read-only unless the user asks to reopen or change it.

Identify `draft` or `needs-decision` status, open questions, unsupported criteria, and material drift from current code or docs. For a ticket marked `ready` but missing a required design approval, report the exact gap and route it back through `$prepare-task` before dependent implementation; do not launch a second open-ended requirements interview. If new evidence invalidates a recorded decision, explain the conflict and ask only for the new blocking decision, with a recommendation; combine closely related questions when useful. Continue safe independent discovery, propose a focused ticket correction when the contract changes, and do not silently rewrite agreed requirements. A `ready` ticket still goes through Fast/Full routing, applicable Superpowers procedures, and all three DoD layers. Previously completed, still applicable design approval satisfies the design approval gate for its recorded scope; do not repeat `brainstorming` for that same design. Reuse a linked implementation plan if still applicable, otherwise create or revise the plan as its skill requires. Direct task requests without a ticket continue to use the task contract in the working conversation.

## Choose Fast or Full

Apply these rules in order after the initial inspection:

1. Honor a user request for Full. For a requested Fast, still check the risks below and explain any escalation.
2. Choose **Full** if any of these apply: unresolved product decision; public or consumer-facing contract change; data migration or ownership change; authentication, authorization, privacy, or secrets impact; concurrency or cross-process behavior; substantial architecture or deployment change; coordinated changes across module boundaries.
3. Choose **Fast** only when behavior is clear, scope is local, the change is reversible, and no Full trigger remains. Multiple files within one module do not by themselves require Full. A small new feature may remain Fast after any required design approval if its scope stays local.
4. If risk is unclear, inspect the relevant code and contracts. If material uncertainty remains, choose Full and record why. Reassess on scope changes; when a Full trigger appears, pause dependent implementation, preserve completed work, and revise the plan while continuing independent safe work.

Fast means a narrow task contract, concise artifacts where invoked skills permit them, and focused verification. Full means deeper planning, an isolation decision, broader relevant verification, and independent review when available and authorized. Neither mode waives an invoked skill's requirements or grants permission for delegation, production operations, or publication.

## Apply existing skills and DoD

- Use available Superpowers skills when their trigger conditions apply: `brainstorming` for creative work and design approval, `writing-plans` for multi-step implementation, `using-git-worktrees` for isolation, `test-driven-development` for code changes, `systematic-debugging` for failures, `verification-before-completion` for completion claims, and review/branch-completion skills when relevant. If delegation is authorized and the plan suits it, `subagent-driven-development` may apply; otherwise use the applicable non-delegated execution route. Follow each invoked skill's instructions, including its own consent and stop conditions.
- If a **required** skill is unavailable, report which procedure is missing and stop work dependent on it; continue independent discovery or documentation. Do not silently invent a replacement. If independent review is unavailable or unauthorized, perform an explicitly labeled self-review and report `independent review: not run`; ask the user only if independent review is an agreed mandatory gate.
- Check three DoD layers: global (criteria, scope, verification, review, docs, honest report), project (approved mandatory checks plus relevant repository commands), and task-specific behavior and failure cases. Distinguish a known mandatory gate from a merely discovered command. Report each applicable check as passed, failed, blocked, or not run, with command or evidence. Missing project DoD alone does not block completion; a failed or unavailable **known mandatory** check prevents a clean completion claim until fixed or explicitly accepted as an exception.
- Diagnose failed tests or review findings, make justified corrections, and rerun affected checks. Replan when assumptions fail. Stop the repair loop when repeated attempts make no meaningful progress; report the blocker. Continue safe independent work when one gate is unavailable.

## Finish honestly

Before claiming completion, inspect the diff and Git state, verify criteria with fresh evidence, and update docs only when documented behavior or contracts changed. Report the task, mode and rationale; files and documentation changed; acceptance criteria and DoD status; commands actually run and their results; review findings and their disposition; unresolved risks or unknowns; Git state; and the exact user action needed next on a pause or external gate. Distinguish a completed change from a proposal and objective check results from agent judgment.

For work started from a ticket, close that ticket as part of completion only when its acceptance criteria and all applicable mandatory DoD checks pass, or a mandatory exception was explicitly accepted and recorded. Make a focused ticket edit: set `Status: done`, preserve `Created`, add `Completed: YYYY-MM-DDTHH:MM:SSZ`, and record concise completion evidence with the checks actually run, results, and relevant code or diff paths. Preserve human notes and agreed requirements. A failed, blocked, or unrun mandatory check leaves the ticket open and the report states why; do not claim `done` from planned checks. `done` means verified local task work, not commit, merge, deployment, or publication. After closing a child, report the first remaining child in the main ticket's current order and any decision or dependency gate; do not skip a blocked child. Close a grouped `00-main.md` only after all agreed children are `done` **and** its overall integration criteria are verified; the last child's closure alone does not close the main ticket.

Local implementation and reversible checks follow the user's task authorization and environment permissions. Destructive data operations, production actions, commit, push, PR creation, merge, and deployment require explicit authorization for that action or clear earlier authorization in the current task. Prepare a reviewable diff and proposed commit or PR text before seeking any remaining decision. Branch-completion options do not authorize a selection by themselves.
